# 创作者主页对话化、只读模板与静态交付设计

## 目标

将创作者申请、个人名片创建和更新流程收敛为清晰的 Agent 主导体验：

1. 小而封闭的决定由宿主原生弹窗承接；资料收集保留自然语言输入；
2. Bonjour Card 作为只读预览模板，不再暴露低代码编辑器；
3. 人类个人主页与 Agent Markdown 入口各司其职，避免 URL／Markdown 标记混写；
4. 所有自定义作者页最终只上传已经构建的静态页面 ZIP，不上传框架源码。

本文补充而不替代现有实现中的源稿恢复、同路由更新、正式模板清单、签名和版本下载契约；本设计只改变用户交互、模板展示形态与最终上传契约。

## 非目标

- 不创建 Agent 与右侧网页之间的共享草稿；
- 不承诺右侧模板中心一定能被完全移除；
- 不把人类个人主页改成 Markdown 页面，或删除 `.md` Agent 入口；
- 不在平台侧引入云端 React／Vite／Node 构建服务；
- 不让浏览器页面传入任意 URL、源码目录、资料、Merchant、release 或发布参数；
- 不改变资格审核、页面归属、预览、上传、发布、回滚与并发保护的既有授权边界。

## 1. 对话与弹窗的分工

### 1.1 使用宿主原生选择弹窗的条件

使用 `AskUserQuestion`（或当前宿主等价的原生单选／确认界面）仅限以下情形：

| 场景 | 选项数量 | 示例 |
| --- | ---: | --- |
| 互斥路径 | 2 | 首次创建先选“查看模板中心 / 自定义个人主页”；自定义后再选“原样导入 / 参考重制” |
| 不可逆外部动作 | 2 | “确认更新名片 / 继续修改” |
| 高风险公开范围 | 2 | “先改平台昵称 / 接受当前昵称继续” |
| 已由平台返回的有限候选 | 2–3 | 多商家、多个已验证模板、多个已验证来源入口 |

弹窗必须有明确动作含义，不得用“是 / 否”代替有语义的选项；宿主支持时保留自定义输入。用户已经用自然语言明确表达选项时，不再重复弹窗。

### 1.2 保留自由输入的条件

以下内容不能拆成连续弹窗：简历、项目材料、链接集合、头像、介绍、联系方式、公开范围的补充说明，以及超过三个且可组合的资料选择。Agent 应一次邀请用户直接发送已有材料，统一整理为“可直接使用 / 待确认公开 / 缺失”，再只对真正需要决定的单项使用弹窗。

没有宿主弹窗能力时，Agent 以相同语义的简短编号选项回退；回退不能额外制造一次确认，也不能让用户重述已给出的资料。

### 1.3 实施边界

付费 Skill 已有 `AskUserQuestion` 的来源选择、媒体选择和最终发布确认规则。个人名片流程复用这一交互政策，不复用付费 Skill 的业务状态或作品发布命令。所有最终页面发布仍只保留一次确认。

## 2. 模板选择：能力增强与可靠回退

### 2.1 基线：右侧只读预览

默认流程继续使用已签名模板目录：Agent 读取 production manifest、在对话中展示可选模板、右侧打开目录或用户要求的模板预览。右侧页面仅用于查看；模板选择、资料输入与发布确认仍由 Agent 在对话中完成。

此基线是第一期交付，必须独立可用，不依赖宿主回传事件。

### 2.2 可选增强：受限模板回传

只有满足全部条件时，才允许“使用此模板”在右侧点击后自动回到当前对话：

1. 宿主明确声明并实际支持 `viceme.template.use` 回传；
2. 宿主验证模板页来源属于官方模板 origin；
3. 事件 payload 严格为 `{ type: "viceme.template.use", id, version }`；
4. Agent 重新从本次已验证 manifest 核对 `id + version` 为 production 模板后才下载源码；
5. 端到端测试证明点击只插入一条可见用户选择，不自动创建、上传、发布或携带资料。

当前已知模板目录只定义了这项第二期协议，不能据此假设宿主已实现。实现前必须在真实 WorkBuddy 环境做一次受控验证；失败、缺失或不支持时，保持 2.1 的右侧预览基线，不能伪造“已选中”。

付费 Skill 的 onboarding Widget 只支持“预设口令 → `sendPrompt`”，不是通用模板创建器，不能直接改作模板中心。若未来需要内置模板选择，应新建小型模板选择 Widget，只传模板 ID/版本并采用上述相同校验与回退。

## 3. Bonjour Card 从低代码编辑器变为只读预览

### 3.1 内容权威性

Agent 在本地工作副本中根据已确认资料生成模板数据并构建页面。页面本身不再创建或持久化可编辑草稿；用户想改姓名、简介、作品、封面、联系方式、标签或排版时，直接向 Agent 描述修改。Agent 重新生成本机预览，用户只在最终预览节点确认发布。

### 3.2 保留与移除

| 类型 | 处理 |
| --- | --- |
| 已渲染的身份、作品、标签与联系方式 | 保留 |
| 作品／外部链接查看与打开动作 | 保留；仅在链接存在时可用 |
| 页面内的只读提示、无障碍焦点与关闭预览 | 保留 |
| “添加 Block”、空状态添加入口 | 移除 |
| 个人资料编辑按钮、Block 编辑按钮 | 移除 |
| 作品／联系方式选择器、编辑表单、图片上传、保存、删除 | 移除 |
| 浏览器本地编辑状态、由编辑器产生的本地持久化 | 移除 |

链接查看不等于编辑：可继续显示链接预览或打开外部链接，但不得借此出现可写表单。发布按钮不属于模板内部编辑器；它由 Agent 的最终确认流程和 CLI 控制。

### 3.3 验收

- 页面没有 input、textarea、file input、添加／编辑／保存／删除动作；
- 作品与联系方式仍可查看或打开，且不存在链接时不提供虚假可点击控件；
- Agent 修改数据后重新构建的预览与最终 ZIP 相同；
- 模板视觉结构不因移除编辑器而被重做为另一套版式；
- 键盘焦点只经过保留的链接和查看操作。

## 4. 人类页、Markdown 与 URL 安全

### 4.1 路由职责

`creatorIdentity.profileUrl` 是人类访问的自定义静态个人页；`creatorIdentity.markdownUrl` 是 Agent 可读取的 Markdown 入口。两者由 CLI / Shop 的本次返回提供，不由 Agent 拼接、推断 handle 或从页面文字还原。

申请与更新默认只使用 `profileUrl`。只有用户主动要求“查看原始内容”或排查时，才展示／打开 `markdownUrl`。个人页不能被“统一改成 Markdown”替代，否则会破坏自定义视觉、预览和静态资产边界。

### 4.2 文本与 URL 的分离规则

- URL 只作为经过 URL 解析校验的链接目标使用；
- 用户可见链接采用标准 Markdown 链接或宿主链接卡，例如 `[查看个人页](<真实 URL>)`；
- 不得输出 `**<真实 URL>**`、把 URL 拼进加粗文本，或将 Markdown 标记、标题、中文说明和 URL 一起传给路由 helper；
- 不得自行 encode、decode、截断或改写 CLI 返回的绝对 URL；
- 发布、预览和回滚都继续使用结构化 CLI 字段，不从聊天渲染文本读取 URL。

### 4.3 回归证据

CLI／Skill 内容测试至少覆盖：带 Unicode 或 percent-encoded path 的真实 `profileUrl`、`markdownUrl` 仅在显式请求时展示、链接目标不含 `*` 或显示文本、以及 Agent 不会把 Markdown URL 当作发布目标。真实 WorkBuddy 环境还需要一次可视验收，确认链接卡与原生渲染不再把标记带入地址。

### 4.4 首次创建前不暴露个人页链接

创作者资格申请成功、但该创作者还没有可用页面 release 时，`profileUrl` 只能被视为平台预留地址，不能视为可访问个人页。此时 Agent：

- 不展示、不打开、不声称“当前个人主页入口是”该 URL；
- 不提供“查看当前内容”或“打开个人页”一类会指向该地址的链接；
- 只说明“申请已提交／审核中；现在可以开始准备个人名片”，然后进入两级路径选择：先选模板中心或自定义个人主页；自定义后再选原样导入或参考重制。

只有首次页面完成构建、静态 ZIP 检查与预览，并且 upload／publish 成功后，Agent 才从本次结构化 CLI 返回中取回实际 `profileUrl`，以标准链接告知用户“个人页已创建，可在这里查看”。更新已有页面时，只有已确认存在 active release 的 `profileUrl` 才可在流程开始时展示。

该规则优先于“申请后立即打开个人页”的旧文案；它避免新账号预留地址在首个 release 之前返回 404，也避免把审核通过后的自动公开误说成当前已可访问。

## 5. 导入入口与个人页支持范围

### 5.1 先识别材料，再决定路径

Agent 不把“用户给了一个链接或图片”一概当作可上传页面。尚无 active release、且用户还没有用自然语言明确选定路径时，WorkBuddy `AskUserQuestion` 先提供恰好两个语义不同的入口：

1. **查看模板中心**：读取并展示所有已验证的 production 模板；用户选择某个模板后才 list／fetch／打开该模板的预览，Bonjour 只是其中一个模板；
2. **自定义个人主页**：不是空白页起点，选择后再进入下面两条互斥子路径。

选择“自定义个人主页”后，再提供恰好两个入口：

1. **原样导入我的主页**：用户提供自己拥有或明确获授权的静态 HTML ZIP、可构建源码目录，或可访问的源码仓库；
2. **参考网页／截图重制**：用户提供自己的网页 URL、截图或参考案例，Agent 提取视觉语言、信息层级和可公开内容，再用用户资料重制静态页。

用户已经用自然语言清楚选定模板中心、某个已验证模板、原样导入或参考重制时，不再重复弹出同义选择器。没有宿主原生提问时，以同样两级语义的简短编号选项回退，不得把模板中心与两条自定义子路径摊成一次三选一。

| 用户提供的材料 | 处理方式 | 能否承诺原样导入 |
| --- | --- | --- |
| 自己的静态 HTML ZIP | 检查入口、资源和 manifest，预览后上传 | 可以 |
| 自己的 React／Vite／Next 源码或仓库 | 本地构建为静态包，再检查、预览和上传 | 可以，但上传的是构建产物 |
| 只有自己的网页 URL | 读取页面作为内容与视觉参考；若无源码／ZIP，按“参考重制”处理 | 不可以 |
| 截图或参考网站 | 提取布局、视觉语言与信息层级，用用户资料重新制作 | 不可以 |
| 头像、作品封面等单张图片 | 作为用户确认可公开的页面素材；必要时先询问用途与公开范围 | 不适用 |
| 已发布 ViceMe 页 | 有平台可恢复的原始源稿时继续修改；否则按重制后替换同一路由处理 | 不从线上页面反推源码 |

“网页 URL”本身不是源码授权或可构建项目。公开网页可能依赖服务端、登录态、动态接口或受保护资源；即使页面可读取，也不能承诺抓取后得到可发布的 1:1 页面。截图同样只用于参考，不复制他人内容、品牌或受保护素材。

### 5.2 个人页的可发布边界

个人页支持 Agent 根据用户确认的资料生成或修改：身份信息、头像／封面、简介、经历、作品卡、图片、外部链接、联系方式、标签、静态版式和链接查看／跳转。所有内容修改都在对话中完成，预览页面只用于查看和打开链接。

导入的页面可保留其已有的静态视觉、文本、图片、CSS 与前端交互；但最终 release 不支持依赖平台外服务端运行的登录、数据库写入、支付、私有 API、SSR、Node 服务或任意运行时构建。此类功能必须在导入前移除、改为静态展示／外链，或另行走网站功能接入流程。

## 6. 静态页面 ZIP 交付契约

### 6.1 区分“导入来源”和“最终上传物”

用户可授权 Agent 读取自己的目录、ZIP、仓库或站点作为导入来源。React、Vite、Next 静态导出或普通 HTML 都可以是**制作来源**；但最终进入 `merchant page inspect/upload` 的唯一上传物是已构建的静态页面 ZIP：

```text
ZIP 根目录
├── viceme-page.json
└── 任意安全相对路径下的 HTML 入口、JS、CSS、图片、字体和其他静态资源
```

直接把 React 源码、`package.json` 与未构建的 `src/` 当作可运行页面上传不被支持。若 Agent 无法可靠构建用户授权的源码，必须说明无法生成可发布静态包，并让用户提供可构建来源或已经导出的静态 ZIP；不得上传源码碰碰运气。

### 6.2 路由与资源适配

静态平台不提供 SPA history fallback。对 React SPA，Agent 在拥有可靠源码时处理相对资源 base 与适用的 hash 路由，再在嵌套 iframe 预览中检查首页、内部跳转、前进／后退和刷新。静态多页页面与已经可运行的 HashRouter 不强制转 React。

平台继续做 archive 结构校验、manifest／entry 校验、路径安全校验和大小限制；不引入平台远程 Node 构建器，也不把本机预览成功误报为线上发布成功。

### 6.3 用户文案

对外统一称为“导入你的主页并生成可发布的静态页面包”。不要让用户理解 React、路由器或 build 细节；只有构建失败且需要来源时，才用白话说明“这份工程还不能导出为可发布页面，需要原始项目配置或已导出的网页包”。

## 7. 实施顺序与所有权

### 阶段 A：流程与回归保护

1. 定位当前正式发布的 `become-a-creator`、`customize-your-profile-page`（或其仓库构建来源）和宿主提示词；避免修改旧副本或同名历史 Skill。
2. 为个人名片流程加入弹窗／自由输入分流规则与 URL 文本分离规则。
3. 补充静态 ZIP 作为最终上传物的流程边界、构建失败文案与回归测试。

### 阶段 B：Bonjour 只读化

1. 从模板源码删除所有编辑器 UI、表单、文件上传与本地编辑状态；
2. 保持数据驱动渲染、链接查看和预览；
3. 构建，完成嵌套路径预览与键盘走查；
4. 更新模板版本、目录预览和签名产物，保证历史版本不被覆盖。

### 阶段 C：可选的内置模板选择

只有阶段 A、B 已发布且宿主回传能力经真实验证后，才实现受限模板回传或独立模板选择 Widget。该阶段失败不会阻止 A、B 发布。

## 8. 完成定义

本改造完成时：

- 对话中小选择与最终发布确认用原生弹窗，资料包收集仍可一次自由输入；
- 不支持回传时，用户仍可在右侧安全查看模板并在对话中选择；
- Bonjour 预览没有编辑器入口，所有修改由 Agent 完成；
- 人类主页和 Markdown 入口的链接不再混写，含特殊字符的真实地址可正确打开；
- 首次申请后、首个页面尚未发布时不展示预留 `profileUrl`；首个 release 发布成功后才提供已验证的个人页链接；
- Agent 以两级选择区分模板中心与自定义个人主页；模板中心中的 Bonjour 与其他 production 模板均在用户选择后才加载；自定义下再区分原样导入和网页／截图参考重制，不把 URL 或截图误称为可 1:1 导入源码；
- 个人页只承诺静态内容与交互，依赖服务端／私有 API 的功能不会被误上传为可运行页面；
- 每个上传 release 都是经过检查与预览的静态 ZIP，框架源码从不被当成可运行上传物；
- 既有审核、发布确认、同路由替换、访问控制与回滚不被削弱。
